# Story 7.3: Default seguro de `users.role` (`manager`) e auditoria dos admins em produção

**Status:** InReview (implementação concluída; CA05, a auditoria em produção, continua pendente com o Rafael antes do merge de 7.1/7.2)

**Sprint:** a definir (@po)

**Dono:** @data-engineer (Dara). Execução da auditoria em produção: Rafael (acesso ao servidor)
**Spec:** `docs/superpowers/specs/2026-10-07-landing-page-design.md` (v0.1, aprovada), seção 6 (Gate admin); Story 7.2, Q-C
**Código alvo:** `vinia-src/backend` (migration e teste) e `vinia-docs/docs/DEPLOY-HOSTINGER.md` (guia)

## Story

Como **Rafael (dono do Vinia)**, quero que um usuário criado sem informar o perfil nasça como `manager` (e não como `admin`), e ter certeza de que só eu sou `admin` em produção, para que o Gate `manage-demo-requests` da Story 7.2 nunca exponha nome, e-mail e telefone dos pedidos de demonstração a quem não deve.

---

## Contexto

Decisão do Rafael (2026-10-07), Story 7.2, Q-C, risco **ALTO** avaliado pelo @po:
- A coluna `users.role` é criada com `->default('admin')` na migration `0001_01_01_000000_create_users_table.php` (linha 20). Quem cria um usuário sem informar `role` gera um **admin**.
- O backoffice **não tem tela de cadastro de usuário**: em produção os usuários nascem por `php artisan tinker`, e o único exemplo do guia (`vinia-docs/docs/DEPLOY-HOSTINGER.md` §4.3, linha 164) usa `'role' => 'admin'`. Quem copiar o exemplo para o restaurante de um cliente cria um admin.
- Com o Gate da 7.2 (`User::isAdmin()` = `role === 'admin'`), todo admin vê a lista inteira de pedidos (dado pessoal, LGPD; critério de sucesso §1.4 da spec: "qualquer outro perfil não acessa").
- Os testes não pegam o problema: `UserFactory` usa `manager` por padrão e `AdminSeeder` (`admin@vinia.app`, senha `password`) não deve rodar em produção (guia §4.2).

**Esta story bloqueia o merge das Stories 7.1 e 7.2 na `main`** (o deploy é automático a cada push na `main` e roda `migrate --force`), mas **não** bloqueia a implementação delas.

Estado real do código (`vinia-src/backend`):
- `database/migrations/0001_01_01_000000_create_users_table.php` linha 20: `$table->string('role')->default('admin');` — **não se edita** (migration já aplicada em produção; editá-la não altera o banco).
- `database/migrations/` mais recente: `2026_06_18_200007_create_ai_interactions_table.php`. A migration nova usa o timestamp da data de criação (via `php artisan make:migration`).
- `database/factories/UserFactory.php`: `role => 'manager'`; estado `admin()` define `role => 'admin'` e `restaurant_id => null`.
- `database/seeders/AdminSeeder.php` (`role => 'admin'`, explícito) e `DemoSeeder.php` (`role => 'owner'`, explícito): não dependem do default.
- `app/Models/User.php`: `#[Fillable([... 'role', ...])]`; `isAdmin()` retorna `role === 'admin'`.
- `phpunit.xml` usa SQLite em memória; o CI (`.github/workflows/deploy.yml`) roda `php artisan test` em **SQLite e MySQL 8**. A migration precisa passar nos dois. Laravel `^13.8`: `->change()` é nativo (sem `doctrine/dbal`) e **exige reafirmar todos os modificadores da coluna**.
- Mudar o default **não altera linhas existentes**: admins já criados continuam admins. Por isso a auditoria manual é parte da story.

## Dev Notes

### Migration
```php
// backend/database/migrations/<timestamp>_change_users_role_default_to_manager.php
return new class extends Migration {
    public function up(): void
    {
        Schema::table('users', function (Blueprint $table) {
            $table->string('role')->default('manager')->change();   // reafirma NOT NULL implícito de string()
        });
    }

    public function down(): void
    {
        Schema::table('users', function (Blueprint $table) {
            $table->string('role')->default('admin')->change();     // reabre o risco: avisar no comentário
        });
    }
};
```
`php artisan make:migration change_users_role_default_to_manager` gera o timestamp correto. Conferir no MySQL do CI e no SQLite local (no SQLite o `change()` recria a tabela internamente; `RefreshDatabase` cobre).

### Teste
Arquivo sugerido: `backend/tests/Feature/UserRoleDefaultTest.php` (ou `tests/Unit/Models/UserModelTest.php`, junto de `ComensalSessionModelTest`). Usar `->fresh()` após `create()` (o Eloquent não conhece o default do banco até recarregar). Inspecionar o default pelo esquema (`Schema::getColumns`) é frágil entre SQLite e MySQL (formato do default); preferir o teste de comportamento.

### Guia (`vinia-docs`)
Alterar a linha 164 (`'role' => 'admin'` → `'role' => 'owner'`) e acrescentar 1 ou 2 frases em §4.3 sobre `admin` reservado ao operador. O repositório do guia é o `vinia-docs`, não o `vinia-src` (mesma observação da Story 7.1, CA24). Não editar nenhuma outra parte do guia.
