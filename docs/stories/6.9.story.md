## Story

Como **gestor de restaurante** que usa o backoffice no computador (muitas vezes por horas e em ambientes claros), quero escolher entre **seguir o sistema, claro ou escuro**, e que o sistema **guarde a minha escolha na minha conta** (valendo em qualquer navegador ou computador em que eu entrar), para trabalhar com conforto e legibilidade sem o backoffice "piscar" ou perder o tema quando navego entre as telas.

## Contexto

O backoffice é **só escuro**: fundo `gray-950`, painéis `gray-900`, campos `gray-800`, texto branco e acento roxo. O Rafael quer o mesmo recurso que o comensal ganhou no tablet (6.8), agora **por usuário**. O tablet resolveu com tokens CSS trocados por tema; o backoffice é outra pilha (Blade + Livewire + Tailwind 4, sem React), então a solução é parecida na ideia e diferente na mecânica. Esta story **reaproveita a paleta e as decisões da 6.8** (papiro `#F9F6F0`, grafite `#1C1C1C`, `color-scheme`, `meta theme-color`, script anti-flash, contraste AA calculado) e **não** reaproveita código (o tablet é TypeScript).

**Cores hoje: classes Tailwind fixas, sem token.**
- `resources/css/app.css` tem 9 linhas: `@import 'tailwindcss'`, dois `@source` e um `@theme` só com a fonte. Nenhuma variável de cor, nenhum `dark:`, nenhum `@custom-variant`.
- 532 ocorrências de classe de cor em 10 arquivos (layouts 46 + 46, login 28, dashboard 16, `wine-form` 105, `restaurant-settings` 67, `tablet-list` 66, `wine-list` 64, `wine-import` 50, `demo-request-list` 44). Conjunto distinto de ~60 classes. **Os 7 arquivos de tela ficam na 6.9b; os 3 de casca (2 layouts + login, 120 ocorrências) ficam aqui.**
- **Dois layouts idênticos:** `components/backoffice-layout.blade.php` (usado por `<x-backoffice-layout>` no dashboard e por `#[Layout('components.backoffice-layout')]` em `DemoRequestList`, `TabletList`, `WineImport`) e `backoffice/layouts/app.blade.php` (usado por `->layout('backoffice.layouts.app')` em `WineList`, `WineForm`, `RestaurantSettings`). O **login** (`auth/login.blade.php`) é um HTML à parte, **sem Livewire e sem Alpine**. Hoje **nenhum dos três tem `<meta name="csrf-token">`**; o `@csrf` está só nos formulários (login e logout).
- `resources/js/app.js` está vazio. O Alpine vem embutido no Livewire 4 e só existe nas páginas com `@livewireScripts` (não no login).
- **Padrão do projeto para o backoffice** (`routes/web.php`): páginas são componentes Livewire de página inteira (`Route::get('/wines', WineList::class)`) dentro de `Route::middleware('auth')`; as ações "de sessão" são **controllers simples** (`AuthController`: `login`, `logout`, via `POST`); a landing usa `throttle:demo-requests`, um `RateLimiter::for(...)` definido no `AppServiceProvider::boot()` (5/min por IP, com `->response(...)` próprio). Não há API de backoffice além do Livewire. O `AuthController` fica em `app/Http/Controllers/Backoffice/`.
- **Exceções em JSON (achado do @po, crítico para o endpoint):** `bootstrap/app.php` tem `$exceptions->shouldRenderJsonWhen(fn (Request $request) => $request->is('api/*'))`. Esse callback **substitui** o `expectsJson()` do Laravel: fora de `api/*`, **mesmo com `Accept: application/json`**, a falha de validação vira **redirect 302** com erros na sessão e a falta de sessão vira **302 para `/backoffice/login`**. O `fetch` segue o redirect e recebe **200** (HTML), o que pareceria sucesso. Por isso a 6.9a **amplia** esse callback para a rota do tema (CA03) e o JS só considera sucesso o **`204`** (CA13).
- **Cache HTTP hoje:** o Laravel/Symfony responde, sem cabeçalho explícito, `Cache-Control: no-cache, private` (o `TabletSpaTest` já afirma esse valor). O `public/.htaccess` **não** tem regra de cache do LiteSpeed (`CacheLookup`, `E=cache-control`) e só define `Cache-Control` para os arquivos do PWA em `/tablet/`. Não há como ver no repositório se o Cache Manager/CDN do hPanel está ligado para o domínio: isso é verificação de produção (@devops, CA19).
- **Deploy:** `scripts/deploy.sh` (na raiz do `vinia-src`) roda `artisan down --retry=15` → `git pull` → `composer install` → troca de assets → **`artisan migrate --force`** → `optimize:clear`/`optimize`/`view:cache` → `queue:restart` → `artisan up`; se algo falha, o `trap` de saída roda `artisan up` (o site volta com o código novo). Banco de produção: "MySQL/MariaDB do hPanel" (`DEPLOY-HOSTINGER.md` §1); o CI testa em SQLite e MySQL 8.
- **Modelo:** `app/Models/User.php` usa atributos PHP `#[Fillable(['name','email','password','role','restaurant_id'])]` e `#[Hidden]`, `casts()` com `email_verified_at`, `password` (hashed) e `restaurant_id`. `UserFactory` define `role = manager`, `restaurant_id` via factory; estado `admin()`. `AdminSeeder` (`firstOrCreate` de `admin@vinia.app`) e `DemoSeeder` criam usuários sem informar tema (null serve). Migration anterior sobre `users`: `2026_10_07_171230_change_users_role_default_to_manager` (padrão de comentário: story, o que muda, "sem UPDATE", `down()` com aviso). **O deploy (`scripts/deploy.sh`) roda `artisan down` → `artisan migrate --force` → caches (`view:cache`) → `artisan up`**: a migration roda sozinha, em manutenção, em produção (MySQL).
- **Navegação Livewire (achado crítico):** as páginas de vinhos usam `wire:navigate`. No `livewire.js`, `swapCurrentPageWithNewHtml` chama `replaceHtmlAttributes(newHtml)` (~linha 12832): **copia os atributos do `<html>` da página nova e remove os que o HTML novo não tem**; a `<meta name="theme-color">` também é reconciliada com a do servidor; um script inline idêntico (mesmo hash) **não roda de novo**. **Efeito com tema por usuário:** quando o servidor renderiza o `data-theme` (preferência `light` ou `dark`), a navegação **preserva** o atributo (vem na resposta nova). Mas para quem tem `theme = null` (segue o sistema) o servidor **não** sabe o tema efetivo (depende do `matchMedia` do navegador), então não emite `data-theme`, e a navegação **o apaga**. Logo, **a reaplicação em `livewire:navigated` continua obrigatória** (CA08). Também há duas corridas: (i) o gestor troca o tema e navega antes de o `PATCH` terminar (a página nova vem com o tema antigo); (ii) o Livewire guarda páginas em cache para o botão "voltar" (snapshot com o tema de antes). A reaplicação pelo estado local cobre as duas.
- **Mesma origem do tablet:** o PWA do tablet roda em `/tablet/` no mesmo domínio e usa `localStorage['vinia.theme']` (6.8). O backoffice **não pode** reutilizar essa chave; com a decisão 7 do @po ele não usa `localStorage` nenhum (CA07).
- **Paginação (vendor):** a view `tailwind` do Livewire usa variantes `dark:` que seguem `prefers-color-scheme` do sistema. É tratada na 6.9b; o `@custom-variant dark` que a corrige é declarado aqui (CA10).
- Testes: 150+ no backend com `withoutVite()`. Nenhum afirma classes de cor. `phpunit.xml`: `CACHE_STORE=array`, `SESSION_DRIVER=array`, SQLite em memória. O CI roda os testes em SQLite **e** em MySQL 8.

Corpo JSON `{"theme": "light"|"dark"|null}`; validação `['present', 'nullable', 'in:light,dark']`. Sucesso: grava e responde `204`. Valor inválido (`"blue"`, `"system"`, `"Dark"`, número, booleano, array, campo ausente): `422` JSON e **nada é gravado**. String vazia `""` vira `null` (middleware do Laravel) e grava "Sistema" (`204`). Sem sessão: `401` JSON. Repetir o mesmo valor é idempotente (`204`). Não regenera a sessão nem mexe em outros campos do usuário. **Para que `422`/`401` saiam em JSON**, `bootstrap/app.php` passa a `shouldRenderJsonWhen(fn (Request $request) => $request->is('api/*', 'backoffice/tema'))` (hoje só `api/*`: sem a mudança, os dois viram redirect 302); nenhuma outra rota muda de comportamento
- [x] **CA04**: **Autorização:** o controller grava em `$request->user()` e **em nenhum outro**. Um `id`, `user_id`, `email` ou `user[id]` enviado no corpo/query/rota é **ignorado**; um usuário **não consegue** alterar o tema de outro (teste com dois usuários: A envia o id de B, o tema de B permanece igual e o de A muda). Sem rota com `{user}` na URL
- [x] **CA05**: **Throttle e CSRF:** rota com `throttle:backoffice-theme`, limiter nomeado definido em `AppServiceProvider::boot()` no padrão do `demo-requests`: **30 requisições por minuto, chaveadas pelo id do usuário autenticado** (fallback IP), resposta `429` JSON. O 31º pedido no minuto recebe `429` e **não grava**; outro usuário não é afetado. **CSRF:** a rota fica no grupo `web` (verificação de token ativa); as páginas autenticadas emitem `<meta name="csrf-token" content="{{ csrf_token() }}">` (hoje não existe) e o JS envia `X-CSRF-TOKEN`; pedido sem token válido recebe `419` (HTML; o controle trata qualquer status diferente de `204` como falha, CA13). O JS envia `Accept: application/json`. Obs.: o Laravel desliga a verificação de CSRF em testes automatizados, então o `419` é conferido na conferência manual (CA21), não no PHPUnit

### Renderização no servidor, sem flash e `wire:navigate` (D6, D7, D10)

- [x] **CA06**: **O servidor emite o tema na primeira resposta.** Os **dois layouts** e o **login** incluem o mesmo partial (CA11) que renderiza: (a) usuário autenticado com `theme = 'light'` ou `'dark'`: `<html lang="pt-BR" data-theme="{theme}" data-theme-pref="{theme}">` e `<meta name="theme-color">` com `#F9F6F0` (claro) ou `#030712` (escuro); (b) autenticado com `theme = null`: `data-theme-pref="system"`, **sem** `data-theme` (quem decide é o script, CA07) e `theme-color` `#030712`; (c) **login / não autenticado**: **nenhum** dos dois atributos (o script segue o sistema, CA07). `lang="pt-BR"` mantido. Para (a), o tema correto aparece mesmo com JavaScript desligado
- [x] **CA07**: **Script inline, síncrono, estático** no `<head>` (partial único), **antes** do `@vite(...)` e do `@livewireStyles`, nos dois layouts e no login. Ordem de resolução do tema efetivo: `data-theme-pref` do `<html>` = `light`/`dark` → vale; `system`, ausente (login) ou valor desconhecido → `matchMedia('(prefers-color-scheme: light)')` casa → `light`, senão `dark` (inclui sem `matchMedia`, `no-preference` e erro, com o `matchMedia` em `try/catch`). Define `document.documentElement.dataset.theme` e o `content` da **única** `<meta name="theme-color">`. **O script não lê nem grava `localStorage`/`sessionStorage`** (decisão 7; o texto do script não contém `localStorage`, então também não há colisão com a chave `vinia.theme` do tablet). O texto do script é **estático** (sem `nonce`, sem dado de usuário embutido: o hash do Livewire precisa ser idêntico em todas as páginas; o que é por usuário vai nos **atributos** do `<html>`)
- [x] **CA08**: **O tema sobrevive à navegação Livewire.** O script registra **uma única vez** (guarda `window.__viniaThemeBound`) um ouvinte de `livewire:navigated` que reaplica o tema efetivo: a partir do `data-theme-pref` da página nova (quando existe) e, em segundo plano, do **estado em memória mais recente** (variável do script na janela, que sobrevive ao `wire:navigate`; a escolha feita pelo controle e ainda não confirmada pelo servidor vence uma resposta velha; cobre a corrida "troquei e naveguei antes do PATCH terminar" e a página do cache do "voltar"). Reaplica também a `theme-color` e o estado do controle (`aria-checked`, `tabindex`). Atualizações de componente (morph) e ações Livewire (salvar, filtrar, paginar, abrir modal) **não** alteram o `<html>`. Critério visual: no tema claro, navegar entre telas **não pisca o escuro**; se a conferência manual mostrar um quadro escuro, o @dev troca a espera do evento por um `MutationObserver` em `<html>` (atributo `data-theme`), síncrono. Recarga completa (F5, login, logout) segue o CA06/CA07
- [x] **CA09**: **Entre abas e dispositivos:** outra aba, outro navegador ou outro dispositivo pegam a preferência salva **na próxima carga de página ou navegação** (o servidor renderiza `data-theme`/`data-theme-pref`; no `wire:navigate` o `data-theme-pref` da página nova é reaplicado, CA08); não há atualização ao vivo entre abas nem entre dispositivos (aceito: sem `localStorage`, sem WebSocket). ### Riscos
- **Migration em produção:** adiciona coluna nullable em `users`, executada pelo `migrate --force` do deploy em manutenção (`artisan down`). Mitigação: sem `UPDATE`, sem default, sem índice; MySQL 8 faz `ADD COLUMN` nullable de forma instantânea; testada em SQLite e MySQL 8 (CA01/CA18); `down()` reversível (apaga só a preferência). Se a migration falhar, o deploy trata como falha de `migrate`; o @devops confere o `deploy.sh` (o `artisan up` do trap). O código novo **exige** a coluna: não deployar o código sem rodar a migration (o script já ordena migrate antes de `up`).
- **Cache de página / CDN (LiteSpeed):** o `data-theme` por usuário na resposta não pode ser cacheado de forma compartilhada, senão vaza o tema (e, pior, páginas autenticadas). Mitigação: CA19 (`cache.headers:no_store;private` explícito no grupo `backoffice`, teste automatizado e verificação do hPanel/cabeçalhos reais pelo @devops antes do merge). Q6.9-O.
- **Falha que parece sucesso (achado do @po):** com o `shouldRenderJsonWhen` atual, `422`/`401` viram redirect e o `fetch` vê `200`. Mitigação: ampliar o callback (CA03) **e** só aceitar `204` no JS (CA13).
- **Múltiplos dispositivos e abas:** a preferência chega na próxima carga/navegação (CA09). Dois dispositivos trocando ao mesmo tempo: vale o último `PATCH` a chegar (aceito).
- **`wire:navigate` apaga atributos do `<html>`** para quem segue o sistema (sem `data-theme` do servidor) e traz página velha após troca rápida: reaplicação em `livewire:navigated` com estado local (CA08), `MutationObserver` como plano B. É o risco técnico principal.
- **Falha de gravação vs. UI otimista:** reverter com aviso (CA13); sessão expirada mostra o aviso e a próxima navegação vai ao login.
- **Autorização:** o único id é o da sessão; teste com dois usuários (CA04). Coluna fora do `fillable` evita mass-assignment em formulários futuros.
- **Abuso:** throttle 30/min por usuário (CA05); o endpoint só grava uma string curta.
- **Tema claro incompleto até a 6.9b:** a 6.9a não vai sozinha para a `main` (ver "Divisão").
- **Colisão de chave no `localStorage`** com o tablet: eliminada (o backoffice não usa `localStorage`, decisão 7).
- **CSRF ausente hoje nos layouts:** o meta `csrf-token` é adicionado (CA05); sem ele o `PATCH` falharia com `419`.
- **Mudança de comportamento para quem tem o sistema claro** (decisão 10/Q6.9-B): comunicar ao Rafael antes do merge.
- **Cores do Tailwind em `oklch`:** o teste usa os hex de referência; o @dev confere contra o compilado.
- **Script inline e CSP:** nenhuma CSP no projeto; script estático, sem `nonce`.
